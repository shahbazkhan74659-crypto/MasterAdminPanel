# Technical Decisions

These decisions were made during prior planning discussions, before any production code was written, originally recorded in `docs/DESIGN.md` and `docs/tech.md`. Both files were migrated into this 6-file documentation system (2026-09-08) and then deleted — their content now lives here (and in `PROJECT.md`/`ARCHITECTURE.md`) rather than in `docs/`. Where original reasoning was not captured at the time, this is marked explicitly rather than guessed.

## Decision: A shared "Content Admin API" protocol, not a per-CMS scraper

- Status: Accepted
- Date: Prior to 2026-09-07 (exact date not captured; locked as of the 2026-09-07 commit that introduced the design/tech docs)
- Context: The owner repeatedly needs an admin/CMS UI for websites they build, and was building one bespoke UI per project.
- Decision: Build one admin panel that speaks a single protocol — the Content Admin API (auth, list collections, get a collection's schema, CRUD on records, media upload/listing, search) — that any backend can implement. The panel does not know about specific CMS platforms.
- Reasoning: Avoids rebuilding a one-off admin UI per project. Two tiers of implementer are anticipated: sites the owner builds (primary v1 target, implement the contract natively) and third-party platforms like WordPress/Shopify (would need a per-platform adapter, not required for v1).
- Consequences: The API's own tech stack is a per-site decision, out of scope for this repository. No spec draft has been written yet — see `PHASES.md`/`TASKS.md`.

## Decision: Site-first, not spec-first — build the Content Admin API before formally documenting its spec

- Status: Accepted (resolved by roadmap ordering)
- Date: 2026-09-08
- Context: The original design record left open whether to lock down the full Content Admin API spec before building anything ("spec-first") or start from one real implementation and generalize the contract from what it actually needs ("site-first").
- Decision: The roadmap (`PHASES.md`) orders Phase 6 (Data Management System engine) and Phase 7 (Content Admin API implementation) before Phase 9 (writing the formal spec document) — resolving the question in favor of **site-first**.
- Reasoning: Owner's phase ordering when defining the roadmap; not separately argued, but the practical effect is that the spec gets written from a real, working implementation rather than designed speculatively up front.
- Consequences: Phase 9's spec document must describe what Phase 6/7 actually built, not aspirational behavior — see `CLAUDE.md` rule 9. If Phase 6/7's implementation changes significantly after Phase 9, the spec document will need a follow-up update to stay accurate.

## Decision: Schema-driven forms are the load-bearing design piece

- Status: Accepted
- Date: Same planning period as above
- Context: For one UI to render editors for arbitrary content types across arbitrary sites, the panel needs to know each field's shape without per-site custom frontend code.
- Decision: The Content Admin API must describe its own schema (field name, type, validation, relations) so the panel can generate the appropriate input (text, rich text, image picker, relation dropdown, date, boolean, array, etc.) generically.
- Reasoning: The same trick LSP uses to let one editor support many languages, scoped here to content administration. Get this right first — everything else (tabs, tree, palette) is UI built on top of it.
- Consequences: This is the piece implementation should prioritize getting right before other UI work — see `TASKS.md`.

## Decision: Image and Video as real schema field types (backend), with dedicated frontend UI

- Status: Accepted
- Date: 2026-09-08
- Context: A review of the original design surfaced a gap — "media upload/listing" was named as a Content Admin API capability, and "image picker" was mentioned narratively as a schema-driven form field type, but neither had any real backend field-type support or dedicated frontend UI scheduled anywhere in the roadmap. No video support was mentioned at all.
- Decision: Image and Video are real field types in the backend content-editing logic ([Phase 6] "Data Management System Backend," alongside the existing text/rich-text/relation/date/boolean/array types) — storing/retrieving image and video field values as part of a record's schema and CRUD flow. The corresponding frontend picker/upload/preview UI is separately scoped to [Phase 27] "Image and Video Field UI (Frontend)."
- Reasoning: Owner's explicit direction, closing a real gap between what the design narratively implied (media handling, an "image picker") and what was actually scheduled to be built (nothing).
- Consequences: A dedicated media library/browser UI (a gallery/grid of uploaded media, search/filter, delete) is still **not** scheduled — Phase 6/27 cover per-record Image/Video *fields*, not a standalone media management surface. How much real editing logic Phase 27 includes (upload/preview/replace only, vs. actual crop/trim-style editing) is not yet decided — see `PHASES.md`'s Phase 27 entry.

## Decision: VS Code interaction metaphor for the panel's UI

- Status: Accepted
- Date: Same planning period as above
- Context: The panel needed a UI/interaction model distinct from a typical boxy CRUD admin UI.
- Decision: Model the panel visually and interactively on VS Code — activity bar (switch sites/workspaces or modules), explorer sidebar (current site's collections/records tree), editor tabs (open records, unsaved-changes dot), editor pane (schema-driven form, or Monaco for raw JSON/HTML/code fields), command palette (quick actions like "New Post"/"Publish"/"Switch Site"), status bar (connected site, environment, save/sync state), split panes (compare two records or environments).
- Reasoning: Not explicitly captured beyond the stated preference; likely follows from the owner's own familiarity with VS Code as a power-user interaction model well-suited to a tree-of-content-types + open-record-tabs structure.
- Consequences: Reusing Monaco (VS Code's real editor component, open source) for code/JSON fields and the SQL console follows directly from this metaphor — see the stack decision below.

## Decision: SQL console connects directly to the database (exception to the API protocol)

- Status: Accepted
- Date: Same planning period as above
- Context: In addition to the schema-driven CRUD path, the owner wants a dedicated SQL query console (its own tab type, VS Code database-extension-styled: table chips, query input, result grid) for personal database work.
- Decision: The SQL console bypasses the Content Admin API entirely and connects directly to the target database. Kept visibly separate (its own tab, its own icon) rather than blended into the record editor, since raw SQL bypasses schema validation and any safety the Content Admin API would otherwise enforce.
- Reasoning: Acceptable specifically because this is a personal-use tool with one trusted operator and no multi-tenant exposure — a materially different trust boundary than the generic content forms, which is why it must stay visibly distinct rather than quietly reusing the same code path.
- Consequences: This directly drove the "not a pure web app" stack constraint below (a browser cannot open a raw DB connection). ~~**Still open, not yet decided**: whether the real implementation defaults to read-only with an explicit confirm step before non-`SELECT` statements, or stays unrestricted.~~ **Resolved 2026-09-09** — see the "SQL console write-safety default" decision below. The *granular*, per-connection version of this question remains open for [Phase 8].
- **Refinement (2026-09-08, Phase 7 planning — see `PHASES.md`):** "connects directly to the target database" covers two cases, not one. For a locally-reachable database (e.g. Phase 1's local Postgres/MySQL/SQLite), the console's backend driver opens a real direct connection, no intermediary. For a real remote website's database that isn't directly network-reachable by the panel, Phase 7's **Content Admin API** implementation is the bridging mechanism — the console's queries get routed through that site's own API server to reach its database. This is still the same trust boundary as "direct" access (unrestricted raw SQL, no schema validation) — it is *not* the schema-driven CRUD path — just carried over a different transport when a raw TCP path isn't available. Do not confuse this bridging role with the Content Admin API's original schema-driven CRUD purpose; a single site's Content Admin API implementation may end up serving both purposes (CRUD forms and raw SQL bridging) but they remain conceptually distinct capabilities.

## Decision: Production stack — Electron + React/TypeScript + Vite + Monaco + Zustand + native DB drivers

- Status: **Superseded** (2026-09-08) — see "Browser-based web app, not an Electron desktop shell" below.
- Date: Same planning period as above (locked alongside the design)
- Context: The SQL console requirement (direct DB connection) rules out a pure web app — a browser cannot open a raw TCP connection to Postgres/MySQL/SQLite. The panel needs a real backend process with native DB drivers.
- Decision:
  - Shell: **Electron** — same foundation as real VS Code; Node.js main process gets direct DB-driver access with no sidecar process needed.
  - UI: **React + TypeScript**, built with **Vite** — matches the component/state model already proven in the prototype; fast dev loop.
  - Code/SQL editing: **Monaco** — real syntax highlighting for the SQL console and any raw JSON/code fields, instead of a plain textarea.
  - State management: **Zustand** — lightweight global store for open tabs, active site, connections; no Redux ceremony needed for a solo project.
  - DB access (SQL console): **Node drivers per engine** (`pg`, `mysql2`, `better-sqlite3`) running in the Electron main process, exposed to the renderer via `contextBridge`/IPC.
  - Content Admin API client: plain `fetch` from the renderer — outbound HTTPS only, to sites the user controls.
  - Secrets (API keys, DB credentials): Electron's built-in **`safeStorage`** — OS-backed encryption, no extra native dependency (skips `keytar`). DB credentials and per-site API keys are two separate secret categories — do not conflate them.
  - Local app state (layout, recent sites, open tabs): **electron-store** — simple JSON persistence for non-secret settings only.
  - Packaging: **electron-builder** — produces a Windows installer for the primary dev machine.
- Reasoning: Everything follows from the direct-DB-connection constraint; see per-row rationale above.
- Consequences: This resolved the "Runtime: local desktop app vs. web app styled to look like VS Code" question that the original design record had listed as open — in favor of Electron. **Reversed 2026-09-08** — see "Browser-based web app, not an Electron desktop shell" below. No implementation was ever built against this stack, so nothing needs unwinding in code.

## Decision: Reject Tauri as the shell

- Status: **Superseded** (2026-09-08) — moot now that the shell itself (Electron) is superseded; kept here as a historical record of the reasoning, since a Rust/Tauri shell could resurface as an alternative if the browser-based direction is ever reversed again.
- Date: Same planning period as above
- Context: Tauri (Rust backend + OS webview) was considered for its smaller binary size and lower memory use, as an alternative to Electron.
- Decision: Rejected.
- Reasoning: The SQL console's DB layer would either need a Rust rewrite (`sqlx`) or a Node sidecar process anyway under Tauri, adding complexity without a clear payoff for a personal, single-user tool where dev speed matters more than binary size.
- Consequences: Revisit only if resource usage becomes a real practical problem — not expected to be reopened otherwise.

## Decision: Browser-based web app, not an Electron desktop shell

- Status: Accepted
- Date: 2026-09-08
- Context: The owner decided to run the panel as a browser-based site rather than an installed Electron desktop app, superseding the earlier Electron/Tauri-shell decision above. This does not remove the original constraint that drove that decision — a browser still cannot open a raw TCP connection to Postgres/MySQL/SQLite for the SQL console — it moves where that constraint is satisfied: a real backend server process now holds the native DB drivers (still `pg`/`mysql2`/`better-sqlite3`, still Node.js) and the browser talks to it over HTTP/WebSocket instead of an Electron main process talked to over IPC.
- Decision: Build the panel as a client (React + TypeScript, Vite) + backend server (Node.js) web app, deployed as a hosted site rather than packaged as a desktop installer.
- Reasoning: Owner's explicit direction ("just use it as a browser based site"), prioritizing browser accessibility over an installed desktop app.
- Consequences:
  - Everything Electron-specific from the superseded stack decision no longer applies: `safeStorage` (secrets), `electron-store` (local settings), `electron-builder` (packaging), and `contextBridge`/IPC (renderer↔main communication).
  - What still carries over unchanged: React + TypeScript + Vite (frontend), Monaco (Monaco is web-native — it works in a plain browser at least as well as in Electron), Zustand (frontend state), and the `pg`/`mysql2`/`better-sqlite3` drivers (now living in a backend server instead of an Electron main process).
  - A backend server framework/runtime choice is now needed (not yet decided — see Open decisions below).
  - Secrets storage (API keys, DB credentials) needs a new server-side mechanism to replace `safeStorage` — not yet decided.
  - A new requirement that didn't exist for the desktop app: **the site needs its own authentication in front of it**. A desktop app installed only on the owner's machine was implicitly trusted because only the owner could open it; a browser-based site is reachable by anyone who has the URL unless it's gated. See the "Single-user login" decision below.
  - Hosting is decided — see the "Render free tier + UptimeRobot" decision below.

## Decision: SQL console write-safety default — read-only, confirm:true required for writes

- Status: Accepted
- Date: 2026-09-09
- Context: The "SQL console connects directly to the database" decision above left open whether the real implementation defaults to read-only with a confirm step, or stays unrestricted. [Phase 5] "SQL Console" was scoped to resolve this basic global posture as part of its own completion criteria (see `PHASES.md`) — distinct from [Phase 8] "SQL Console Access/Modification Policy," which covers a more granular, configurable, per-database/per-connection policy layer built on top of whatever basic default Phase 5 established. `DECISIONS.md`'s own "Still open" note above, and `CLAUDE.md`'s project notes, had both drifted toward attributing the whole question to Phase 8 alone — this entry and the corrections alongside it fix that.
- Decision: The console defaults to **read-only**. Any statement classified as a write requires the request to explicitly pass `confirm: true`, or it's rejected with `409`. Classification is a pragmatic, honest-effort scan (not a full SQL parser): a statement is read-only if its first keyword is in an allowlist (`SELECT`, `SHOW`, `EXPLAIN`, `DESCRIBE`/`DESC`, `PRAGMA`, `WITH`), and additionally, the whole statement is scanned for write keywords (`INSERT`/`UPDATE`/`DELETE`/`MERGE`/`DROP`/`ALTER`/`TRUNCATE`/`CREATE`/`GRANT`/`REVOKE`) as a safety net for CTEs (`WITH ... AS (...) INSERT ...`) — a design that can rarely over-block (e.g. a CTE literally named `update_log` used only in a `SELECT`) but never under-blocks, which is the correct direction to err. Requests containing more than one SQL statement (detected via a naive semicolon check, not real statement parsing) are rejected outright at `400`, closing the `SELECT 1; DROP TABLE users;` bypass rather than trying to classify each statement independently.
- Reasoning: Owner's direct choice. A safe-by-default posture costs nothing for the console's only current use (Phase 5's own verification and future ad-hoc personal queries) while a real accidental-write mistake is exactly the failure mode a personal admin tool with direct DB access should guard against by default.
- Consequences: Implemented in `backend/src/sqlConsole/classify.ts` (`isWriteStatement`, `hasMultipleStatements`), enforced in `backend/src/sqlConsole/sqlConsoleRoutes.ts` before any connection is touched. Known, accepted gaps — not full SQL-parser rigor, single-statement-only, `PRAGMA` treated as always read-only even for the rare pragma that mutates connection state — are deliberately left for [Phase 8] to tighten if the owner wants a more rigorous or configurable policy later.

## Decision: Data management schema via auto-introspection + column-naming convention for special field types

- Status: Accepted
- Date: 2026-09-09
- Context: [Phase 6] "Data Management System Backend" needed a way to determine a collection's schema (field names/types) without a separate config file to author and maintain, while still supporting the field types `PROJECT.md`/`DECISIONS.md` describe (rich text, image, video, relation) that don't map to any native SQL column type.
- Decision: Schema is **auto-introspected** from the database's real columns (native type → base type: text/integer/float/boolean/date/other). A **naming convention on the column name** tags the special types raw introspection can't express: `_richtext`, `_image`, `_video` (each requires the underlying column be `text`-based), and `_id_relation` (requires `integer` or `text`, and resolves its target collection by trying `<stem>`, `<stem>s`, `<stem>es` against the engine's real table list). If a suffix matches but the base type is incompatible, or a relation target can't be resolved, the suffix is ignored — the field falls back to its plain base type with `specialType: null`, and a server-side warning is logged, rather than erroring. Scoped to the same Phase 1b local databases Phase 5 already targets — not remote sites (that's Phase 7's job).
- Reasoning: Owner's direct choice. Avoids a second, hand-maintained source of truth about a collection's shape that could drift from the real table; the naming convention is a pragmatic, zero-config way to express the handful of extra field types this project actually needs.
- Consequences: Implemented in `backend/src/dataManagement/fieldTypes.ts` (`mapNativeType`, `applySpecialType`) and `introspection.ts` (`getTableSchema`, primary-key detection per engine). A known, accepted gap: SQLite has no native boolean/date type, so a declared column type that doesn't literally contain a recognizable type-name substring (e.g. `DATETIME`) falls to `baseType: "other"` rather than being inferred — not solved further this phase. A table with no primary key, or a composite one, still returns a schema but rejects `:id`-based record operations with a 400 (`supportsRecordOperations: false`) rather than attempting to support it.

## Decision: Real, single-step file-upload handling for Image/Video fields

- Status: Accepted
- Date: 2026-09-09
- Context: The original schema-driven forms decision named an "image picker" narratively but never specified real upload mechanics. [Phase 6]'s own scope note left this "to be defined... as the owner directs," and the owner was asked directly what they wanted.
- Decision: Uploading a file to an Image/Video field is a **single backend request** — no separate "upload, get a path back, then PATCH the record" flow. `POST /data-api/:engine/:collection/records/:id/upload/:field` (using `multer`, a new dependency) validates the target field is actually tagged `image`/`video` in that collection's introspected schema, confirms the record exists, saves the file to a new gitignored `backend/media/<engine>/<collection>/<field>/` with a generated filename (never the client's original filename) and a mimetype check against the field's declared type, then writes the resulting served path (via a new `/media` static mount) directly into the record's column as part of the same request/response.
- Reasoning: Owner's explicit direction — an admin/agent should be able to upload a file directly without knowing or constructing a file path themselves; the backend handles storage and record-linking together. This is real backend work (an API endpoint), distinct from [Phase 27]'s separate job of building the actual frontend picker/preview UI component.
- Consequences: Re-uploading to a field that already holds a path leaves the old file on disk untouched — no cleanup/orphan-deletion logic this phase (an accepted, deliberate limitation; full lifecycle management would be more than a personal tool needs right now). File-size/mimetype limits (10MB images, 200MB video, filtered by MIME prefix) are basic sanity bounds, not a security-hardened upload pipeline. `backend/media/` is gitignored, same treatment as `local-data/`.

## Decision: Login mechanics — server-side session cookie, bcrypt hashing, Postgres-backed storage

- Status: Accepted
- Date: 2026-09-09
- Context: The "Single-user login" decision above committed to building a login flow but explicitly left its mechanics open: session vs. token auth, password hashing, and where the owner account's credentials live. [Phase 4] "Login Auth Engine/Flow" was scoped to resolve all three.
- Decision:
  - **Auth mechanism**: server-side session via an httpOnly cookie (`express-session`), not a JWT/token.
  - **Password hashing**: bcrypt-format hashing via the `bcryptjs` package (pure JS, produces standard `$2a$`/`$2b$` hashes — same format as native `bcrypt`, chosen to avoid Windows native-build friction; no perf concern at single-user, occasional-login scale).
  - **Credential storage**: a new `users` table in Phase 1a's `adminpanel_app` Postgres database — the local database already provisioned specifically for the panel's own data. Schema created via a plain `CREATE TABLE IF NOT EXISTS` run at server startup (`backend/src/db/schema.ts`); no migration framework introduced for one table.
  - **Session storage**: sessions are also persisted in `adminpanel_app` (via `connect-pg-simple`, its own auto-created `session` table), not in-memory — chosen so logins survive `tsx watch`'s dev-time restarts and Render's eventual free-tier cold starts (Phase 30).
  - **Account creation/reset**: a one-off CLI script (`backend/src/scripts/seedOwner.ts`, run as `npm run seed:owner -- <username> <password>`) is the only way the account gets created or its password changed. No signup flow exists or is planned — consistent with the project's single-owner, no-multi-account scope.
- Reasoning: Owner's direct choices, aligned with the project's stated non-goals (single operator, no multi-account system) and with reusing infrastructure already committed to (Phase 1a's Postgres) rather than introducing new storage just for auth.
- Consequences: `backend/src/index.ts` gained `express.json()` and `express-session` middleware; a shared `pg.Pool` module (`backend/src/db/pool.ts`) now exists, scoped only to `adminpanel_app` — a new pattern distinct from `testRoutes.ts`'s per-request connections to the Phase 1b target databases, which remain unchanged. No existing route (e.g. `/test-api/*`) was gated behind auth by this decision — per the roadmap, real route-gating is Phase 24's job, once a real UI exists to protect. Production HTTPS deployment (Phase 30) will need `cookie.secure: true` and `app.set("trust proxy", 1)` (Render terminates TLS at a proxy) — flagged in code as a comment, not solved yet. `SESSION_SECRET` was added to `.env.local` (already gitignored) as this app's own runtime config — distinct from [Phase 10]'s "secrets storage mechanism," which covers secrets for *managed sites*, not this app's own session-signing key.

## Decision: Phase 7 implemented as a direct remote-DB connection, not an API bridge

- Status: Accepted
- Date: 2026-09-09
- Context: [Phase 7]'s objective/scope (see `PHASES.md`) originally framed the Content Admin API as an HTTP protocol a remote site's own backend would implement, which this panel's backend calls as a client — bridging the SQL Console (Phase 5) to a site whose database isn't directly network-reachable, with queries "technically routed through the site's own API server" (see the "SQL console connects directly to the database" decision's Phase 7 refinement note above). Mid-implementation, the owner gave a hard, direct instruction: no code in the target site's own repository may be touched at all, to test this or for any other reason. The site chosen to exercise this phase was Portfolio (`C:\Portfolio`), a real site the owner already runs, using its **local dev Postgres** database (not its production Neon database) — its connection details read directly from Portfolio's own untouched, gitignored `.env` file.
- Decision: Since nothing can be added to Portfolio's (or any connected site's) own codebase, Phase 7 does not implement an HTTP API that a site exposes. Instead, this panel's own backend is given the target site's real database credentials directly and connects to it with its own native driver — exactly the same direct-connection model [Phase 5] already uses for the three local Phase 1b databases, just pointed at a second, real site's actual database instead of one this panel provisioned for itself. Scope was also narrowed to only the SQL-bridging capability Phase 7 explicitly names — the full originally-designed Content Admin API surface (auth, collections, schema, CRUD, media, search, exposed over HTTP to arbitrary sites) was not built this phase and remains open for whenever it's actually needed.
- Reasoning: Owner's explicit, direct constraint against touching a connected site's own code, given mid-session. A real remote database that accepts direct network connections (Portfolio's Postgres, like the local Phase 1b databases and unlike, say, a database that's only reachable from inside a site's own private network) doesn't actually need a site-implemented bridge to be queried this way — the bridge mechanism described in the original Phase 7 framing remains the right approach specifically for a site whose database genuinely isn't directly reachable, which was not the case here.
- Consequences: `backend/src/sqlConsole/connections.ts` gained a `remoteSites` registry (Postgres-only, id-keyed, built from `REMOTE_SITE_<ID>_*` env vars in `.env.local` — interim placement, same caveat as every other credential in that file; real secrets storage is still Phase 10's job). `adapters.ts`'s `runPostgresQuery`/`listPostgresTables` were generalized to take a `Pool` parameter instead of closing over the fixed local `pgPool`, so the same logic serves both the local `postgres` engine and any registered remote site (Phase 6's `dataManagement/introspection.ts`, the other caller of `listPostgresTables`, was updated to keep passing the local `pgPool` explicitly — no behavior change there). ## Decision: SQL Console access/modification policy — protected-table-name write block

- Status: Accepted
- Date: 2026-09-09
- Context: [Phase 5] built a single, global write-safety rule (read-only by default, `confirm:true` unlocks any write) applied identically to every connection. [Phase 7] extended the same console to a real external site's database (Portfolio's local dev Postgres) with no additional protection — a confirmed write against *any* table on *any* connection, including Portfolio's real Django `auth_user` table (which holds real password hashes), would have succeeded. [Phase 8]'s own scope explicitly calls for this to be decided as something more than a single on/off switch, potentially scoped per-database/per-connection.
- Decision: Every table whose name contains "user", "credential", "session", "password", or "secret" (case-insensitive substring match) can be **read but never written to** — not even with `confirm:true` — enforced uniformly across every connection today (all three Phase 1b local engines and every Phase 7 remote site). The policy is modeled per-connection *and* per-table (a specific connection could override the global table rules later, though nothing does yet) and per **both** read and write (only write is actively restricted by this rule; read stays open everywhere, including on protected tables, so the same structure can carry a future read-restricting rule without a rework). Configured as a static code module (`backend/src/sqlConsole/policy.ts`), the same interim pattern as `connections.ts`'s registry — no new database table, no env vars; change it, restart the server.
- Reasoning: Owner's direct choices on all four points (the concrete rule, the per-connection+per-table granularity, modeling both read and write, and static-code-module config) — the pattern-based table-name rule needs no schema awareness or per-site configuration to already cover the real, sensitive tables the console can reach today (most notably Portfolio's `auth_user`/`auth_user_groups`/`auth_user_user_permissions` and `django_session`), and to require no extra setup, generalizing automatically to any future connection with a similarly-named table.
- Consequences: `extractWriteTargetTable` (in `policy.ts`) is a pragmatic, honest-effort regex extraction of the table a write statement targets — same "not a full SQL parser" philosophy `classify.ts` already established for read/write classification — recognizing `INSERT INTO`/`UPDATE`/`DELETE FROM`/`DROP TABLE [IF EXISTS]`/`ALTER TABLE`/`TRUNCATE [TABLE]`. An unrecognized statement shape (notably `CREATE TABLE`, `GRANT`, `REVOKE`) returns `null` and is **never** treated as protected — a known, accepted gap, in the safe direction (under-blocking an edge case, never over-blocking or misidentifying a normal statement). `sqlConsoleRoutes.ts`'s two `POST .../query` handlers were refactored into one shared `gatedQuery` helper so the policy check applies identically to local engines and remote sites from a single choke point, rather than being duplicated (and risking drift) across both routes. Verification deliberately proved the block using Portfolio's real `auth_user` table with **no `confirm` sent at all** (a `403` instead of the previous `409` proves the policy runs independently of the confirm gate) — the full confirmed-write round-trip proof ran only against a throwaway table on AdminPanel's own local test database, never against Portfolio's real data, consistent with [Phase 7]'s own verification discipline.

## Decision: Phase 23 implementation — full-shadow-copy drafts, always-overwrite deploy, protected-table policy reused at deploy too

- Status: Accepted
- Date: 2026-09-11
- Context: The "Staging layer for data-management edits" decision above committed to the feature and its rough shape but left several concrete questions open for when [Phase 23] actually started: how a draft is stored (full copy vs. diff/patch), what happens if the live row changes after a draft was started (conflict handling), whether staging supports batched multi-record deploys, and how this relates to the still-open "versioning/history in the editor pane" item. The owner resolved all four directly when implementation began.
- Decision:
  - **Draft storage**: a full shadow copy of the record's would-be values (`drafts.draft_values JSONB`), not a diff/patch — `saveDraft` always merges new field values onto the existing draft (or the live row, if none) and stores the complete result, so deploying a draft is a plain overwrite with no patch-application logic needed.
  - **Conflict handling**: deploy always overwrites live with the draft's values — no conflict detection, no "live changed since you staged this" warning, in v1. The simplest behavior for a single-operator personal tool.
  - **Batching**: per-record only. One `drafts` row per `(engine, collection, record_id)` (`UNIQUE` constraint, upserted); no multi-record batch-deploy mechanism exists or is implied by the schema. Explicitly deferred to a later, unscheduled enhancement.
  - **Versioning/history**: kept genuinely separate from staging's core mechanics — `drafts` models only "what's currently being edited." But a lightweight, cheap forward-compat hook was added anyway: an append-only `deploy_log` table (`deployed_values JSONB`, populated from the exact row `updateRecord` returns at deploy time — zero extra queries), so a future history/versioning feature only needs a new read endpoint and some UI, not a schema rework. No read endpoint or UI exists against `deploy_log` in this phase.
  - **Protected-table policy applied at deploy too**: [Phase 8]'s SQL Console protected-table-name policy (`isProtectedTable`, tables matching "user"/"credential"/"session"/"password"/"secret") is reused verbatim at the staging layer's deploy step — a draft can always be staged against any table (staging never touches the live database), but deploying it is blocked (`403`, checked before the `confirm:true` gate, same ordering as the SQL Console's `gatedQuery`) if the target table is protected. This does **not** fold the SQL Console into the staging model — it reuses one pure `tableName → boolean` predicate at a second call site because the policy's actual purpose (never let this tool overwrite credential/session/password tables) doesn't care which code path triggered the write.
- Reasoning: Owner's direct choices on all four points, given directly when Phase 23 implementation began. Full-shadow-copy storage is the simplest representation that makes "deploy = overwrite" trivially correct. Always-overwrite conflict handling matches the tool's existing single-operator trust model (same reasoning as the SQL console's own write-safety posture). Per-record-only avoids speculative batch-deploy machinery nothing needs yet. The `deploy_log` compromise (real table, no feature built on it yet) avoids both extremes — neither ignoring the future versioning need entirely nor over-building a full history UI/API this phase doesn't call for. Applying the protected-table policy at deploy closes a real gap: without it, a table the SQL Console can never write to would have been writable through the staging/deploy path instead, defeating the policy's purpose.
- Consequences: New tables `drafts`/`deploy_log` in `backend/src/db/schema.ts`'s `ensureSchema()`. New `backend/src/dataManagement/staging.ts` (`saveDraft`/`getDraft`/`listDrafts`/`discardDraft`/`getDraftWithLiveDiff`/`deployDraft`) and `backend/src/dataManagement/stagingRoutes.ts` (`POST/GET/DELETE .../draft`, `POST .../deploy`), mounted alongside `dataRoutes.ts` at `/data-api`. `staging.ts` deliberately contains no per-engine SQL of its own — `deployDraft` calls [Phase 6]'s `updateRecord` directly for the actual write, which means schema drift between stage-time and deploy-time (a column renamed/dropped after staging) surfaces automatically as a normal `ValidationError`/`400`, not a special case this phase had to build. `listDrafts` exists but isn't exposed as a route this phase (no UI need for it yet — forward-compat only, same spirit as `deploy_log`). The existing "Versioning/history" open-decision entry below is updated to note `deploy_log`'s existence. See `TASKS.md`'s Phase 23 completion entry and `ARCHITECTURE.md` for the full implementation detail, including the frontend wiring (one hardcoded demo record, real Save/Deploy actions in the Phase 22 split-pane UI).

## Decision: Phase 24a implementation — full-schema server-side login validation, strict rate limit, auth gate placement

- Status: Accepted
- Date: 2026-09-11
- Context: [Phase 24a] needed several concrete calls the phase's own scope didn't pre-decide: whether server-side login validation reuses the frontend's full password-complexity Zod schema or a narrower shape-only check (the former risks rejecting the real owner's login if their pre-existing password doesn't satisfy the regex — it was seeded via `seedOwner.ts` before this complexity rule existed, with zero validation of any kind); the exact rate-limit threshold on `POST /auth-api/login`; and whether `/media` should be gated alongside `/sql-console-api`/`/data-api`. The owner resolved all three directly.
- Decision:
  - **Full-schema reuse, accepted lockout risk**: `backend/src/auth/loginSchema.ts` (a duplicated copy of `frontend/src/loginSchema.ts` — no shared package exists between the two isolated npm packages, no workspace, no root `package.json`, so this is kept in sync by hand rather than standing up monorepo tooling as a side effect of a login-wiring phase) is applied to every login attempt, complexity rules included. If the real owner's actual password doesn't satisfy it, login will `400` — the resolution path is `npm run seed:owner -- <username> <new-compliant-password>`, not a special-cased bypass.
  - **Rate limit**: 5 attempts / 15 minutes per IP on `POST /auth-api/login` only (not `/logout`/`/me`), via `express-rate-limit`. Strict, on purpose. A `DISABLE_RATE_LIMIT` env var (set in `.env.local` for local/dev only, never production) is read live per-request in the limiter's `skip` function — not cached at import time — so it works whether the dev server was started directly (`npm run dev`) or spawned/reused by Playwright's `webServer`.
  - **`/media` gated too**: alongside `/sql-console-api` and `/data-api`, behind the same `requireAuth` middleware, for consistency with "the whole UI sits behind the gate" — and it already had to move after the session middleware to fix a real pre-existing ordering bug (see the implementation note in `PHASES.md`'s 24a entry), so gating it at the same time was effectively free.
- Reasoning: Owner's direct choices on all three points. Full-schema reuse over a shape-only subset was chosen with the lockout risk explicitly named and accepted rather than silently worked around — the alternative (weakening server-side validation to avoid the risk) was rejected in favor of a known, simple recovery path if it happens. The strict 5/15min threshold prioritizes blocking real brute-forcing over convenience, with the env-gated bypass specifically designed to survive both of Playwright's server-launch modes rather than just the common case.
- Consequences: If the real owner's login 400s after this change, that is expected (not a bug) and resolved via re-seeding, not a regression to chase. The `DISABLE_RATE_LIMIT` env var must never be set in production (Render, [Phase 29]) — nothing currently enforces this at the code level, it's a documented operational discipline only. `requireAuth` is mounted once in `index.ts` after the whole `/auth-api` router (not inside individual routes), so any future route added under `/auth-api` is public-by-default unless deliberately moved after the gate — worth remembering when [Phase 24f] or later phases add new `/auth-api` routes (e.g. password reset).

  **Outcome, 2026-09-11**: the anticipated risk materialized — the real owner's pre-existing password did not satisfy the complexity schema. Resolved exactly via the planned path: `npm run seed:owner -- Shahbaz <new password>` (the account's username, confirmed from the real `users` table; the new password itself is not recorded here — never put real credentials in project docs). The owner then logged in successfully through the real app, verified directly by the owner (Claude does not have and was not given the real password) — see the "Remote real-login verification via a temporary ngrok tunnel" decision below for how, since the owner was away from the machine at the time.

## Decision: Remote real-login verification via a temporary ngrok tunnel; `vite.config.ts` allows ngrok hosts

- Status: Accepted
- Date: 2026-09-11
- Context: [Phase 24a]'s one remaining verification step — the real owner logging in through the actual app — needed the owner directly (Claude does not have and should not be given the real password), but the owner was away from the machine, reachable only via the Claude mobile app continuing this same terminal session remotely. The owner asked for a way to reach the local dev app from their phone.
- Decision: Used the already-installed, already-authenticated `ngrok` CLI (a standalone Windows tool, not a project dependency) to tunnel `http://localhost:5175` (the frontend dev server, which already proxies `/auth-api`/`/data-api` to the backend) to a temporary public HTTPS URL. Before exposing it, the backend was restarted with its login rate limit genuinely enabled (`DISABLE_RATE_LIMIT` unset for that run — normally bypassed for local dev/e2e, per the "Phase 24a implementation" decision above), specifically so a public-facing login couldn't be brute-forced during the tunnel's lifetime. Vite's dev-server host-check initially blocked ngrok's hostname (`Blocked request... not allowed`) — fixed by adding `server.allowedHosts: ['.ngrok-free.dev', '.ngrok-free.app', '.ngrok.io']` to `frontend/vite.config.ts`, a permanent, harmless-at-rest config addition (dev-server-only, has no effect in a production build) kept in the repo so a future remote-testing session doesn't have to rediscover the same block. Claude verified the tunnel end-to-end via `curl` (health, `/auth-api/me`, a throwaway wrong-password attempt) but never entered the real owner's password anywhere — that step was the owner's alone, done directly through the browser on their end. Once confirmed, the tunnel was torn down (`ngrok` process killed, URL confirmed offline) and the backend restarted back to normal local-dev mode (rate-limit bypass active again).
- Reasoning: The safety rule against Claude entering real credentials applies regardless of context — a personal single-user tool is not an exception. Tunneling the frontend (not the backend directly) was chosen because Vite's own dev proxy already handles `/auth-api`/`/data-api` forwarding, so one tunnel covers both without any CORS work. Forcing the rate limit on before exposing anything publicly was a deliberate precaution given the whole point of [Phase 24a] is that this login endpoint is now internet-reachable through any tunnel, however temporary.
- Consequences: `frontend/vite.config.ts` now permanently allows ngrok hostnames in dev — worth knowing if a future dev-server security review looks for unexpected `allowedHosts` entries; it has no effect once `vite build` produces a static production bundle. The `ngrok` tool itself remains installed globally (not added to any `package.json`) — nothing in the repo depends on it being present. This is a one-off manual verification aid, not a repeatable/documented remote-dev workflow — if remote testing becomes a regular need, that would warrant its own real decision (e.g. a proper dev-tunnel setup or a staging deployment) rather than repeating this ad hoc.

## Decision: Phase 24a — a genuine, pre-existing protected-table-policy gap surfaced and fixed in test infra, not worked around

- Status: Accepted
- Date: 2026-09-11
- Context: While verifying [Phase 24a]'s gating change, `backend/e2e/staging.spec.ts`'s own protected-table fixture test (`e2e_user_accounts`, deliberately named to contain "user" and exercise [Phase 8]'s protected-table policy) failed on a second run with "relation already exists." Investigation showed this wasn't caused by the auth-gating change: [Phase 8]'s policy correctly blocks `DROP TABLE` on any name containing "user"/"credential"/"session"/"password"/"secret" — which means this fixture's own teardown (`DROP TABLE IF EXISTS e2e_user_accounts`, run automatically via `fixtures.ts`) has silently failed against that policy on every run since [Phase 8] shipped, leaking the table forever. This had simply never been hit before because the test hadn't been run twice against non-fresh state in the same session until now. A direct, ad-hoc DB command to manually drop the stray table was attempted and correctly refused by the session's own safety tooling as an unreviewed destructive action outside the normal test/app path.
- Decision: Did not force the drop through any privileged path. Instead: (1) gave the protected fixture table a per-run-unique suffix (`e2e_user_accounts_${Date.now()}`) so it can never collide with a previous run's leftover — the leak itself is accepted as permanent, harmless local-dev debris, since the policy that causes it is working exactly as intended and must not be weakened for testability; (2) separately made `fixtures.ts`'s `create()` drop-before-create for the general (non-protected-name) case, so an ordinary fixture table left behind by a crashed/interrupted run self-heals on the next run instead of failing.
- Reasoning: The protected-table policy correctly refusing to let anything — including test cleanup — drop a "user"-named table is the policy working as designed ([Phase 8]'s whole point); "fixing" that would mean weakening real security-relevant behavior to make a test cleaner, which is backwards. A unique-per-run name sidesteps the symptom without touching the policy or requiring any manual/destructive intervention.
- Consequences: The local target-postgres dev database will accumulate uniquely-named `e2e_user_accounts_<timestamp>` tables over time, purely as harmless local-dev debris — a human with direct DB access can clean these up manually whenever convenient; nothing in the app or test suite depends on them not existing. `extractWriteTargetTable`'s existing, already-documented CREATE-TABLE gap (see [Phase 11]'s note) plus this DROP-side consequence together mean a protected-named table can be *created* through the SQL Console (the known CREATE gap) but then never dropped through it again (this entry) — worth keeping in mind if a future phase ever needs to actually remove a protected-pattern table for real, which would require a direct DB operation outside the app, not a SQL Console query.

## Decision: Phase 24c implementation — four design forks resolved directly with the owner

- Status: Accepted
- Date: 2026-09-11
- Context: [Phase 24c] ("Editor Pane — Real Record Editing") needed several concrete calls its own scope text didn't pre-decide, each a genuine fork rather than an obvious default — matching the project's established pattern (Phases 18/19/21/22) of resolving these directly with the owner before implementation rather than picking silently.

New tabs opened from the explorer can stage but not deploy — a record edited this way only reached the live database once [Phase 24e]'s split-pane work added a deploy affordance. **Superseded 2026-09-11**: [Phase 24e] resolved this not with a per-tab Deploy button but with one global, site-wide "deploy everything pending" action (see [Phase 24e (split-pane half) implementation] below) — the standalone Compare/`DEMO` tab referenced here no longer exists at all, replaced by a per-tab split/compare `viewMode` toggle.

## Decision: Phase 24e (split-pane half) implementation — split becomes a per-tab toggle; Deploy becomes one global, site-wide action

- Status: Accepted
- Date: 2026-09-11
- Context: The owner reported three real problems with the editor pane as [Phase 24c] left it: the Compare tab opened by default on every app load instead of the editor starting empty; the sidebar's "Open Split View" button always jumped to one hardcoded demo record regardless of what was actually open; and (a direct follow-up) Deploy should not live in per-record panes at all. Each of these maps to a genuine fork the owner resolved directly, matching this project's established pattern.
- Decision:
  - **Default state**: the editor area starts empty on load — no tab, no Compare pane. `activeKey`'s initial state changed from `'compare'` to `''`.
  - **Split becomes a per-tab toggle, not a separate tab**: the sidebar's split-view button now acts on whichever tab is currently active, flipping that tab's own `viewMode` between `'edit'` and `'compare'` in place. No new pane is ever created; there is no longer a standalone "Compare" tab at all. Clicking split with no active tab does nothing except show a small, auto-dismissing "No Tab Selected" tooltip above the button — it does not silently no-op or error.
  - **Split toggle is bidirectional**: clicking the split icon again on an already-split tab reverts it to the normal single-pane view. The icon itself reflects current state (two-pane glyph when not split, single-page glyph when split) so it always shows what the next click will do.
  - **Deploy removed from every per-record pane**: neither the normal single-pane view nor the split/compare view has a Deploy button anymore. Replaced by one global icon button in the sidebar header (positioned left of "Open SQL Console") that deploys **every** pending draft across the whole connected site in one action — explicitly a bulk-only action for now; per-record/selective deploy is a deferred future step, not built.
- Reasoning: Owner's direct choices on all four points. Splitting in place (rather than jumping to an unrelated pane) matches the mental model of "compare *this* record," not "go look at some other fixed record." A real on/off toggle with a state-reflecting icon avoids a dead-end UX (split-with-no-way-back). Making Deploy a single global, site-wide action reflects a deliberate simplification: reviewing and shipping every pending change at once, rather than building (and then having to maintain) a per-record Deploy affordance whose placement had already caused confusion once (the old Compare-only Deploy).
- Consequences: There is currently no way to deploy a single specific record's draft without deploying every other pending draft across the site at the same time — a real, accepted limitation until selective/per-record deploy is built as a future step (not scheduled to any phase). The bulk endpoint (`POST /data-api/:engine/drafts/deploy-all`) reports partial success (`deployed`/`skipped`/`failed`) rather than all-or-nothing, so one protected or invalid draft never blocks the rest from shipping — this asymmetry (single-record deploy is all-or-nothing via 404/403/409/400; bulk deploy always returns 200 with a breakdown) is intentional and should be preserved if a selective-deploy UI is added later. Real multi-site switching (the activity-bar half of [Phase 24e]) remains untouched — the bulk deploy action is scoped to the one hardcoded `postgres` engine/site, same as the rest of the app today.
