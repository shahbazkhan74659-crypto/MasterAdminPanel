## Phase 0 — Pre-Development (Design & Stack Decision)

### Objective
Define the product concept, UI/interaction model, core protocol architecture, and technology stack, and validate the design against a working visual prototype — before writing any production code.

### Scope

**0a. Product & Design Definition**
- Core concept defined: a personal, reusable admin panel driven by a shared "Content Admin API" protocol, rather than a one-off UI per site (see `PROJECT.md`).
- VS Code-metaphor UI mapped out (activity bar, explorer tree, editor tabs, command palette, status bar, split panes) (see `PROJECT.md`, `ARCHITECTURE.md`).
- Schema-driven forms identified as the load-bearing design decision — the API describes its own schema so one UI can render editors for arbitrary content types (see `DECISIONS.md`).
- SQL console scoped as a deliberate, explicit exception to the schema-driven CRUD path — connects directly to the database rather than through the Content Admin API (see `DECISIONS.md`).
- Several product decisions explicitly left open rather than guessed at: spec-first vs. site-first build order, secrets-storage scoping detail, versioning/history in the editor, SQL console write-safety default (see `DECISIONS.md`, `TASKS.md`).

**Status: Complete**, as evidenced by the locked design record in `DECISIONS.md` (originally `docs/DESIGN.md`, migrated).

**0b. Technology Stack Decision**
- Stack originally chosen: Electron + React/TypeScript (Vite) + Monaco + Zustand + native per-engine DB drivers (`pg`/`mysql2`/`better-sqlite3`) + Electron `safeStorage` + `electron-store` + `electron-builder` (see `DECISIONS.md`). Tauri evaluated and explicitly rejected.
- **Revised 2026-09-08**: owner decided to run the panel as a browser-based web app instead of an Electron desktop app — Electron/Tauri, `safeStorage`, `electron-store`, and `electron-builder` are all superseded. React/TypeScript/Vite/Monaco/Zustand carry over unchanged; DB drivers move into a new backend server component; hosting is Render's free tier + UptimeRobot; a single-user login gate is now required (a desktop app didn't need one). See `DECISIONS.md` for the full decision history and what's still open (backend framework, secrets storage, login mechanics).

**Status: Complete**, as a locked direction — see `DECISIONS.md` (originally `docs/tech.md`, migrated, then revised 2026-09-08). Several implementation-level specifics under the new browser-based direction remain open — see `TASKS.md`.

**0c. Visual Prototyping**
- A design canvas prototype (`design/master-admin-panel.html`, plus its source `design/Main.dc.html`/`design/canvas.json`) built and published, demonstrating the VS Code-metaphor UI as a mock frontend only — no real API calls, no real DB connection.

**Status: Complete.** The existing design canvas is sufficient as a design/validation reference — no further prototyping work is scheduled before the owner picks a next real-implementation step (see `TASKS.md`'s Next section for the two candidate directions under consideration).

### Completion Criteria

## Phase 6 — Data Management System Backend (Direct Typed Edits)

### Objective
Build the backend for the "normal" (non-SQL) data management path: directly changing data by typing new values into fields, rather than writing raw SQL (the Phase 5 SQL Console's path). This is the schema-driven CRUD mechanism `DECISIONS.md` calls "the load-bearing design decision" — list a collection, read its schema, and update/create/delete records by field, typed input in, validated write out. **Renumbered 2026-09-08 (was Phase 8) to sit before Phase 7's Content Admin API, since that phase exposes this engine's CRUD logic to remote sites and needs it to exist first — see the note below.**

### Scope
To be defined in further detail as the owner directs. Per the standing convention, this is backend work — the schema-driven CRUD engine/endpoints (list collections, get a collection's schema, create/read/update/delete a record by field) built into the Phase 2 backend server, exercised via Phase 3's blank test page (typing a new value into a plain input and submitting it, not a real schema-driven form UI). **Confirmed by the owner (2026-09-08): this is the same engine as Phase 7's Content Admin API — this phase builds the actual list/read/update/delete-by-schema logic, which Phase 7's Content Admin API is the protocol/interface exposing to remote sites.** One engine, built across both phases, not two separate mechanisms — this is why this phase now comes first. **Includes Image and Video as real field types in the content-editing logic** (owner's direction, 2026-09-08) — not just the "image picker" mentioned narratively in `DECISIONS.md`'s schema-driven forms decision, but actual backend support: storing/retrieving image and video field values as part of a record's schema and CRUD flow, alongside the existing text/rich-text/relation/date/boolean/array field types. The corresponding frontend picker/upload/editing UI for these two field types is separately scoped to Phase 26 — this phase is backend/data-model only.

### Completion Criteria
A real backend endpoint can list a collection/table's records and schema — including Image and Video field types — and accept a typed field value (for text-like fields) or an image/video value (for those two field types) to update (or create/delete) a record, with the change actually persisted to a real database — exercised via Phase 3's blank test page, not a real schema-driven form UI.

**Status: Complete (2026-09-09).** Built the schema-driven CRUD engine against the same three Phase 1b local databases the SQL console (Phase 5) already targets. Schema is auto-introspected from the database's real columns (native SQL type → a base type: text/integer/float/boolean/date/other); a **naming convention on the column name** tags special types raw SQL can't express — `_richtext`, `_image`, `_video` (all require a `text`-based column), and `_id_relation` (resolves its target collection by trying `<stem>`, `<stem>s`, `<stem>es` against the engine's real table list). An incompatible or unresolvable suffix is ignored (plain field, warning logged), not an error. New module `backend/src/dataManagement/` (`introspection.ts`, `fieldTypes.ts`, `validation.ts`, `crud.ts`, `upload.ts`, `dataRoutes.ts`), mounted at `/data-api`: `GET /:engine/collections`, `GET /:engine/:collection/schema`, `GET/POST /:engine/:collection/records`, `GET/PATCH/DELETE /:engine/:collection/records/:id`. Table/column identifiers are only ever taken from introspection's own output (never raw client strings) before being used in a query — the injection guard for this path. A table with no primary key or a composite one still supports `schema`/`collections` but rejects `:id`-based operations with a clear 400 rather than trying to support it. **Includes real Image/Video file-upload handling** (owner's explicit direction): `POST /:engine/:collection/records/:id/upload/:field` (multer, new dependency) validates the field is actually tagged image/video first, saves the file to a new gitignored `backend/media/<engine>/<collection>/<field>/` (generated filename, restricted extension allowlist, mimetype-checked against the field's type), serves it via a new `/media` static mount, and writes the resulting path into the record in the same request — not a separate upload-then-PATCH step. No write-safety gate here (unlike Phase 5) — this is the validated, schema-driven path by construction. Not gated behind the Phase 4 login session — that's Phase 23's job. **Bug caught and fixed along the way:** `better-sqlite3` rejects binding a JS `boolean` directly ("SQLite3 can only bind numbers, strings, bigints, buffers, and null") — fixed by converting booleans to `0`/`1` for SQLite parameter binding only. Verified end-to-end across all three engines: schema introspection correctly tagged a real richtext/image/video column each; full create/read/update/delete round trips; a real file upload whose bytes matched byte-for-byte on retrieval via `/media`, correctly written into the record; the full negative-case matrix (unknown engine/collection/field, wrong type, missing required field, PK-in-body, non-image/video upload target, wrong mimetype, no-PK table); `/test-api/*`, `/auth-api/*`, `/sql-console-api/*` reconfirmed undisturbed; `tsc --noEmit` and `npm run build` both clean.
