# Architecture

This describes the **actual current implementation** — a design/prototype layer plus a minimal Phase 2 backend scaffold, well short of the full production system — followed by the **planned** production architecture. See `DECISIONS.md` for the reasoning behind the planned design and stack.

## System Overview

**Implemented:** The repository holds a published Claude Design canvas, `design/master-admin-panel.html` (a self-contained HTML artifact — an early preview of the Claude Design canvas editor, packaged to run as a published artifact page), plus its editable source files `design/Main.dc.html` (the single artboard's content) and `design/canvas.json` (canvas layout). This is the interactive visual prototype referenced as "Prototype" in the design record (see `DECISIONS.md`) — a mock frontend demonstrating the intended VS Code-styled UI, with no real API calls, no real database connection. An empty `Prototype/` folder exists at the repo root with no content. **As of Phase 2 (2026-09-08):** a real `backend/` Node.js project exists (Express + TypeScript) with a single `GET /health` route. **As of Phase 3 (2026-09-08):** the server also loads `../.env.local` via `dotenv` and mounts three throwaway `GET /test-api/{postgres,mysql,sqlite}` endpoints (`backend/src/testRoutes.ts`) that open real connections to the Phase 1b target databases using `pg`/`mysql2`/`better-sqlite3`, plus a static diagnostic page at `backend/public/test.html` — all explicitly temporary, deleted in Phase 11 once the fuller end-to-end backend pass is done. **As of Phase 4 (2026-09-09):** real login/logout/session-check endpoints exist (`backend/src/auth/authRoutes.ts`, mounted at `/auth-api/*`), gated by nothing yet — no other route is auth-protected (that's Phase 23's job). Credentials live in a `users` table and sessions in a `session` table, both in the panel's own `adminpanel_app` Postgres database (Phase 1a), accessed via a new shared `pg.Pool` (`backend/src/db/pool.ts`) — the first code to actually read the `ADMINPANEL_DB_*` env vars. **As of Phase 5 (2026-09-09):** real SQL console endpoints exist (`backend/src/sqlConsole/`, mounted at `/sql-console-api/*`) — table listing and query execution across all three Phase 1b target databases, with a read-only-by-default/`confirm:true`-for-writes posture enforced before any connection is touched (see `DECISIONS.md`). Also gated by nothing yet, same as `/test-api/*` and `/auth-api/*`. **As of Phase 6 (2026-09-09):** real schema-driven CRUD endpoints exist (`backend/src/dataManagement/`, mounted at `/data-api/*`) — collection listing, auto-introspected schema (with a column-naming convention tagging rich text/image/video/relation fields), and create/read/update/delete by record id, across the same three Phase 1b target databases. Table/column identifiers used in queries are only ever taken from introspection's own output, never raw client input. Also includes real file-upload handling: `POST /data-api/:engine/:collection/records/:id/upload/:field` (via `multer`) saves a file to a new gitignored `backend/media/` and writes its served path (via a new `/media` static mount) into the record in the same request. No write-safety gate here, unlike the SQL console — this path is validated by construction. Also gated by nothing yet, same as the other route groups. **As of Phase 7 (2026-09-09):** the SQL Console (`backend/src/sqlConsole/`) gained a `remoteSites` registry in `connections.ts` — real, external sites' own databases, connected to directly with real per-site credentials (not through any API the site implements). Currently one entry, `portfolio`, pointed at Portfolio's real local dev Postgres database (`C:\Portfolio`'s own `.env`, read but never modified). `adapters.ts`'s `runPostgresQuery`/`listPostgresTables` were generalized to accept a `Pool` parameter (previously closed over the fixed local `pgPool`) so the same query/table-listing logic serves both the local Phase 1b `postgres` engine and any registered remote site. New routes `GET/POST /sql-console-api/sites/:siteId/{tables,query}` sit alongside the existing `/:engine/...` routes, reusing the same `isWriteStatement`/`hasMultipleStatements` safety gate and response shape. This is **not** an HTTP-based Content Admin API that a site's own backend implements — the phase's original "site's own API server bridges to its DB" framing was ruled out mid-implementation by the owner's hard constraint against touching any code in a connected site's own repository; see `DECISIONS.md`'s "Phase 7 implemented as a direct remote-DB connection, not an API bridge" entry. The full, originally-designed Content Admin API surface (auth/collections/schema/CRUD/media/search, exposed over HTTP to arbitrary sites) remains unbuilt. **As of Phase 8 (2026-09-09):** the SQL Console gained a real access/modification policy, `backend/src/sqlConsole/policy.ts` — every table whose name contains "user"/"credential"/"session"/"password"/"secret" (case-insensitive) is read-only, never writable, across every connection (local engines and remote sites alike), enforced regardless of `confirm:true`. `sqlConsoleRoutes.ts`'s two `POST .../query` handlers now share one `gatedQuery` helper (multi-statement check → policy check → confirm check → run) instead of duplicating the safety logic. No frontend application code exists yet — the design canvas above remains the only UI reference until Phase 12.

**Planned:** A browser-based web app (**superseding an earlier Electron desktop-app plan**, reversed 2026-09-08 — see `DECISIONS.md`): a React + TypeScript frontend (built via Vite), styled and structured after the VS Code interface, served by a Node.js backend server, gated behind a single-user login. The frontend talks to two distinct backends: (1) arbitrary remote sites over HTTPS via the Content Admin API protocol (client-side `fetch`, unchanged from the original plan), and (2) this panel's own backend server, which holds the native DB drivers and brokers the SQL console's direct database connections (replacing Electron's main-process/IPC arrangement). Deployment target: Render's free tier + an UptimeRobot keep-alive monitor, the same pattern as the Portfolio project, backed by a Neon Postgres database for the panel's own production data. No planned-architecture code has been written yet — but the full build order is locked: `PHASES.md`'s Phase 0–30 roadmap covers local database setup, the backend server and its login/SQL-console/data-management/Content-Admin-API/secrets pieces, an end-to-end backend test pass, every static UI piece matched to the design canvas prototype, wiring the UI to the backend, Monaco and Zustand build-outs, Image/Video field support, and finally production deployment plus live verification.

## Technology Stack

**Implemented:** `backend/` — Node.js (v24) + Express 4 + TypeScript, run via `tsx` in dev and compiled with `tsc` for production, ESM module format. DB access for the Phase 3 test endpoints uses `pg`, `mysql2`, and `better-sqlite3` (the same drivers the planned architecture locks in below), plus `dotenv` for loading `.env.local`. **As of Phase 4:** `express-session` (session middleware) + `connect-pg-simple` (Postgres-backed session store) + `bcryptjs` (password hashing) added. No frontend framework, Monaco, or Zustand wired in yet.

**Planned** (see `DECISIONS.md` — Electron-specific rows below are superseded; carried-over and new rows reflect the 2026-09-08 browser-based pivot):

| Layer | Choice | Why |
|---|---|---|
| Frontend | React + TypeScript, built with Vite | Matches the component/state model already proven in the prototype; fast dev loop. Unchanged by the browser-based pivot. |
| Backend server | Node.js (specific framework — e.g. Express/Fastify — not yet chosen) | Needed so the browser can reach native DB drivers indirectly; replaces Electron's main process. See Open decisions in `DECISIONS.md`. |
| Code/SQL editing | Monaco (the actual VS Code editor component) | Real syntax highlighting for the SQL console and any raw JSON/code fields. Monaco is web-native, so this is unaffected by the pivot. |
| State management | Zustand | Lightweight global store for open tabs, active site, connections. Unchanged. |
| DB access (SQL console) | Node drivers per engine (`pg`, `mysql2`, `better-sqlite3`), now running in the backend server and exposed to the frontend via an authenticated HTTP/WebSocket API instead of Electron's `contextBridge`/IPC | Implements the "connect directly to the DB" decision (see `DECISIONS.md`), relocated from an Electron main process to a standalone backend server. |
| Content Admin API client | Plain `fetch` from the frontend | Outbound HTTPS only, to sites the user controls. Unchanged. |
| Auth | Single-user login — server-side session cookie (`express-session` + `connect-pg-simple`), `bcryptjs` password hashing, credentials in `adminpanel_app` Postgres (resolved [Phase 4], see `DECISIONS.md`) | The browser-based site is reachable by anyone with the URL, unlike a desktop app installed only on the owner's machine — see `DECISIONS.md`. |
| Secrets (API keys, DB credentials) | Not yet decided — `safeStorage` no longer applies (Electron-only) | Needs a server-side mechanism (env vars, encrypted store, secrets manager) — see Open decisions in `DECISIONS.md`. |
| Local/app state (layout, recent sites, open tabs) | Not yet decided — `electron-store` no longer applies (Electron-only) | Likely browser storage and/or server-persisted settings; not yet chosen. |
| Hosting / deployment | Render free tier + UptimeRobot | Owner's explicit choice, reusing the exact pattern the Portfolio project already runs on. Replaces `electron-builder`/desktop packaging entirely. |

The Electron-vs-Tauri shell decision (and the Tauri rejection reasoning) is now moot given the browser-based pivot — see `DECISIONS.md` for the full history.

## Application Structure

**Implemented:** `backend/src/index.ts` — the Express app bootstrap (`GET /health`, `express.json()`, session middleware, route mounting). Real module structure now exists: `backend/src/db/pool.ts` (shared `pg.Pool` for `adminpanel_app`), `backend/src/db/schema.ts` (`ensureSchema()`), `backend/src/auth/authRoutes.ts` (login/logout/session-check), `backend/src/scripts/seedOwner.ts` (one-off account-seeding CLI), `backend/src/types/express-session.d.ts` (typed session data), and `backend/src/sqlConsole/` — `connections.ts` (persistent per-engine connections to the Phase 1b `TARGET_*` databases), `classify.ts` (write-statement/multiple-statement guards), `adapters.ts` (per-engine query execution and result normalization), `sqlConsoleRoutes.ts` (table-listing/query endpoints), and `backend/src/dataManagement/` — `introspection.ts` (schema/primary-key introspection per engine), `fieldTypes.ts` (native-type mapping + naming-convention special-type tagging), `validation.ts` (create/update value validation), `crud.ts` (list/get/create/update/delete by id), `upload.ts` (multer config + media path helpers), `dataRoutes.ts` (collections/schema/records/upload endpoints). Content Admin API logic still doesn't exist yet (Phase 7 onward). No frontend structure exists yet — only the design canvas artifact described above.

**Planned:** Not yet broken down into concrete modules/files — no code has been written against the now-locked Phase 0–30 roadmap yet (see `PHASES.md`). The product design (see `PROJECT.md`) implies at least: a frontend UI layer (activity bar / explorer / tabs / editor pane / command palette / status bar / SQL Console panel / split panes), a Content Admin API client module, a login/auth flow, a backend-server DB-connection module per supported engine, and a data-management/schema-driven CRUD engine — but no file/module layout has been decided. The roadmap's own ordering is a real architectural signal worth preserving here: backend pieces (server, login, SQL console, data management engine, Content Admin API, secrets) are built and end-to-end tested before any static UI, and every UI piece is built to match the design canvas prototype exactly *before* being wired to the backend — see `PHASES.md` for the full sequencing.

## Component Structure

**Implemented:** The design canvas prototype demonstrates the VS Code-metaphor UI visually (activity bar, explorer tree, tabs, editor pane, command palette, status bar) but as static/mock design content, not real React components.

**Planned:** Real component structure not yet decided. Will need to reflect the VS Code element mapping recorded in `PROJECT.md` (activity bar → site/module switcher, explorer tree → collections/records, tabs → open records, editor pane → schema-driven form or Monaco instance, with a breadcrumb path header, command palette → quick actions, status bar → connection/save state, split panes → record/environment comparison) plus a distinct SQL Console panel (its own icon, per-site, styled after a VS Code database extension: table chips, query input, result grid). Per `PHASES.md`'s locked roadmap, every one of these gets built as a static piece matching the design canvas prototype exactly first (Phases 12–22), then wired to real data (Phase 23), with Monaco (Phase 24) and Zustand (Phase 25) taken from minimal to fully functional afterward.

## Data Flow

**Implemented:** None — no real data flow exists; the prototype has no data fetching or persistence.

**Planned:** Two independent flows, per `PROJECT.md`'s Content Admin API protocol vs. SQL console distinction:
1. **Content Admin API path**: frontend → `fetch()` over HTTPS → a remote site's Content Admin API → schema + records returned → panel renders the appropriate editor for each field type (text, rich text, image, video, relation dropdown, date, boolean, array, etc.) based on the schema the API itself describes. Image and Video are real, first-class field types (backend support in Phase 6, dedicated frontend picker/upload/preview UI in Phase 26 — see `DECISIONS.md`), not just a narratively-mentioned "image picker."
2. **SQL console path**: frontend → authenticated HTTP/WebSocket request → this panel's own backend server → native DB driver (`pg`/`mysql2`/`better-sqlite3`) → direct connection to the target database, bypassing the Content Admin API and any schema validation it would otherwise enforce. Relocated from Electron's IPC/main-process arrangement to a standalone backend server as part of the 2026-09-08 browser-based pivot (see `DECISIONS.md`) — still a deliberate exception, acceptable specifically because this is a personal, single-operator tool. **Implemented as of [Phase 5]**: `POST /sql-console-api/:engine/query` and `GET /sql-console-api/:engine/tables`, across all three Phase 1b target engines, enforcing a read-only-by-default/`confirm:true`-for-writes posture (see `DECISIONS.md`). **Extended as of [Phase 7]**: `GET/POST /sql-console-api/sites/:siteId/{tables,query}` reaches a real, external site's own database (currently Portfolio's local dev Postgres) the same direct-driver way — not via a bridge through that site's own API server, since the site's own codebase was ruled off-limits (see `DECISIONS.md`). **As of [Phase 8]**: both query routes now enforce a protected-table-name write policy (`backend/src/sqlConsole/policy.ts`) ahead of the confirm gate — tables named like accounts/secrets storage can never be written to, confirmed or not. Not yet authenticated — no route currently requires a session; that's [Phase 23]'s job. The "authenticated HTTP/WebSocket" framing above describes the eventual planned state, not the current one.

A third flow now exists that didn't under the desktop-app plan: **login** — the browser client authenticates against the backend server (`POST /auth-api/login`) before reaching either flow above (see `DECISIONS.md`'s "Single-user login" and "Login mechanics" decisions). Implemented as of [Phase 4]: credentials checked against `adminpanel_app`'s `users` table (bcrypt), a session cookie issued and persisted server-side (`connect-pg-simple`). Nothing is gated by this yet — no other route currently requires a session; that wiring is [Phase 23]'s job once a real UI exists.

## State Management

**Implemented:** None.

**Planned:** Zustand for frontend global state — open tabs, active site/workspace, connection status. Per `PHASES.md`'s locked roadmap, Phase 23 wires the UI up with only minimal/ad-hoc state just to make it work, and Phase 25 replaces that with a real, fully-wired Zustand implementation — the same "minimal first, fully functional in a dedicated later phase" pattern used for Monaco (Phase 23 → 24). Persisted local app settings (layout, recent sites, open tabs) need a new mechanism now that `electron-store` no longer applies — not yet decided (browser storage vs. server-persisted, per Open decisions in `DECISIONS.md`). Secrets (API keys, DB credentials) get a real server-side storage mechanism in Phase 10 — not yet built, but no longer entirely undecided-in-direction — keeping the "two distinct secret categories" principle (API keys vs. DB credentials) regardless of mechanism.

## Routing

**Implemented:** None — the prototype is a single static canvas, not a routed application.

**Planned:** Not yet decided — likely still tab/panel-based navigation (VS Code-style, no URL-based routing) within the app shell, plus a real route/redirect for the login gate itself now that the app is browser-based. No decision has been recorded.

## API Architecture

**Implemented:** None.

**Planned:** The **Content Admin API** — a protocol the panel speaks as an HTTP client, not a specific server this repository implements. Any backend can serve it by exposing: auth (get a session/token), list collections, get a collection's schema (field names, types, validation, relations), CRUD on records within a collection, media upload/listing, and search. The schema-driven nature of this API (the server describes its own schema rather than the panel hardcoding it per site) is the core architectural decision this whole project is built around (see `DECISIONS.md`). No spec draft exists yet — per `PHASES.md`'s locked roadmap, a first real implementation is built in Phase 6 (the underlying CRUD engine) and Phase 7 (the protocol/interface layer exposing it) *before* the formal spec document gets written in Phase 9, a deliberate site-first ordering (see `DECISIONS.md`'s "Site-first, not spec-first" decision). The API's tech stack is a per-site decision, out of scope for this repository.

Two tiers of API implementer are anticipated: (1) sites the owner builds, implementing the contract natively — the primary v1 target; (2) third-party platforms (WordPress, Shopify, etc.), which would need a per-platform adapter translating their native API into the Content Admin API contract — not required for v1.

## Data / Persistence

**Implemented:** None.

**Planned:** The panel does not own a *content* database — it either (a) reads/writes remote sites' content through their own Content Admin API implementations, or (b) connects directly to a target database via native drivers for the SQL console. It does need some persistence of its own that didn't exist under the desktop-app plan: at minimum, the single login account's credentials, plus wherever per-site DB credentials/API keys end up being stored server-side. **Implemented as of Phase 4:** the login account's credentials (`users` table) and session data (`session` table, via `connect-pg-simple`) are both persisted in `adminpanel_app`, the local Postgres database provisioned in Phase 1a — the first real use of that database. Per `PHASES.md`'s locked roadmap, the rest is resolved in direction but not yet built: the storage *mechanism* for per-site secrets is decided in Phase 10, and the panel's own production database — a Neon Postgres instance, same pattern as the Portfolio project — is set up in Phase 28, since Render's free tier (the Phase 29 deployment target) has no persistent disk.
