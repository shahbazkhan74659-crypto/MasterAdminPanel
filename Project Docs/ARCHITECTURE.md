# Architecture

This describes the **actual current implementation** — as of [Phase 23] (2026-09-11), a real Express/TypeScript backend (login, SQL console, schema-driven data management with a staging/draft layer, secrets storage) and a real React/TypeScript frontend (every VS Code-metaphor UI piece, matched to the design canvas prototype, with the split-pane view additionally wired to live data for one demo record) — still short of the full production system (no Monaco, no Zustand, no real auth-gating, no production deployment yet) — followed by the **planned** production architecture describing what's still ahead. See `DECISIONS.md` for the reasoning behind the planned design and stack, and `TASKS.md` for exactly which phase is next.

## System Overview

**Implemented:** The repository holds a published Claude Design canvas, `design/master-admin-panel.html` (a self-contained HTML artifact — an early preview of the Claude Design canvas editor, packaged to run as a published artifact page), plus its editable source files `design/Main.dc.html` (the single artboard's content) and `design/canvas.json` (canvas layout). This is the interactive visual prototype referenced as "Prototype" in the design record (see `DECISIONS.md`) — a mock frontend demonstrating the intended VS Code-styled UI, with no real API calls, no real database connection. An empty `Prototype/` folder exists at the repo root with no content. **As of Phase 2 (2026-09-08):** a real `backend/` Node.js project exists (Express + TypeScript) with a single `GET /health` route. **As of Phase 3 (2026-09-08):** the server also loads `../.env.local` via `dotenv` and mounts three throwaway `GET /test-api/{postgres,mysql,sqlite}` endpoints (`backend/src/testRoutes.ts`) that open real connections to the Phase 1b target databases using `pg`/`mysql2`/`better-sqlite3`, plus a static diagnostic page at `backend/public/test.html` — all explicitly temporary, deleted in Phase 11 once the fuller end-to-end backend pass is done. **As of Phase 4 (2026-09-09):** real login/logout/session-check endpoints exist (`backend/src/auth/authRoutes.ts`, mounted at `/auth-api/*`), gated by nothing yet — no other route is auth-protected (that's Phase 24's job). Credentials live in a `users` table and sessions in a `session` table, both in the panel's own `adminpanel_app` Postgres database (Phase 1a), accessed via a new shared `pg.Pool` (`backend/src/db/pool.ts`) — the first code to actually read the `ADMINPANEL_DB_*` env vars. **As of Phase 5 (2026-09-09):** real SQL console endpoints exist (`backend/src/sqlConsole/`, mounted at `/sql-console-api/*`) — table listing and query execution across all three Phase 1b target databases, with a read-only-by-default/`confirm:true`-for-writes posture enforced before any connection is touched (see `DECISIONS.md`). Also gated by nothing yet, same as `/test-api/*` and `/auth-api/*`. **As of Phase 6 (2026-09-09):** real schema-driven CRUD endpoints exist (`backend/src/dataManagement/`, mounted at `/data-api/*`) — collection listing, auto-introspected schema (with a column-naming convention tagging rich text/image/video/relation fields), and create/read/update/delete by record id, across the same three Phase 1b target databases. Table/column identifiers used in queries are only ever taken from introspection's own output, never raw client input. Also includes real file-upload handling: `POST /data-api/:engine/:collection/records/:id/upload/:field` (via `multer`) saves a file to a new gitignored `backend/media/` and writes its served path (via a new `/media` static mount) into the record in the same request. No write-safety gate here, unlike the SQL console — this path is validated by construction. Also gated by nothing yet, same as the other route groups. **As of Phase 7 (2026-09-09):** the SQL Console (`backend/src/sqlConsole/`) gained a `remoteSites` registry in `connections.ts` — real, external sites' own databases, connected to directly with real per-site credentials (not through any API the site implements). Currently one entry, `portfolio`, pointed at Portfolio's real local dev Postgres database (`C:\Portfolio`'s own `.env`, read but never modified). `adapters.ts`'s `runPostgresQuery`/`listPostgresTables` were generalized to accept a `Pool` parameter (previously closed over the fixed local `pgPool`) so the same query/table-listing logic serves both the local Phase 1b `postgres` engine and any registered remote site. New routes `GET/POST /sql-console-api/sites/:siteId/{tables,query}` sit alongside the existing `/:engine/...` routes, reusing the same `isWriteStatement`/`hasMultipleStatements` safety gate and response shape. This is **not** an HTTP-based Content Admin API that a site's own backend implements — the phase's original "site's own API server bridges to its DB" framing was ruled out mid-implementation by the owner's hard constraint against touching any code in a connected site's own repository; see `DECISIONS.md`'s "Phase 7 implemented as a direct remote-DB connection, not an API bridge" entry. The full, originally-designed Content Admin API surface (auth/collections/schema/CRUD/media/search, exposed over HTTP to arbitrary sites) remains unbuilt. **As of Phase 8 (2026-09-09):** the SQL Console gained a real access/modification policy, `backend/src/sqlConsole/policy.ts` — every table whose name contains "user"/"credential"/"session"/"password"/"secret" (case-insensitive) is read-only, never writable, across every connection (local engines and remote sites alike), enforced regardless of `confirm:true`. `sqlConsoleRoutes.ts`'s two `POST .../query` handlers now share one `gatedQuery` helper (multi-statement check → policy check → confirm check → run) instead of duplicating the safety logic. **As of Phase 10 (2026-09-09):** a real secrets storage mechanism exists — `backend/src/secrets/` (`crypto.ts` — AES-256-GCM via `node:crypto`; `store.ts` — `setSecret`/`getSecret`/`requireSecret`), backed by a new `secrets` table in `adminpanel_app` Postgres (added to `ensureSchema()`), with a DB-level `CHECK` constraint separating `db-credential`/`api-key` categories. `connections.ts` changed from synchronous, module-load-time pool construction from `process.env.TARGET_*`/`REMOTE_SITE_*` to an async `initConnections()` reading from this store instead, awaited in `index.ts`'s `bootstrap()`. The real, working `TARGET_*`/`REMOTE_SITE_PORTFOLIO_*` credentials were migrated in via a one-off script (`backend/src/scripts/migrateSecrets.ts`, `npm run migrate-secrets`) and retired from `.env.local` for real — proven by re-running the SQL Console's own Phase 5/7/8 verification with those env vars actually gone. `ADMINPANEL_DB_*`/`SESSION_SECRET` remain untouched, out of this phase's scope (the panel's own runtime config). **As of Phase 11 (2026-09-09):** the project's first real test suite exists — 125 Vitest unit/"component" tests (co-located `*.test.ts` files) covering the pure-function pieces of `secrets/`, `sqlConsole/`, and `dataManagement/`, plus 21 Playwright API-mode e2e tests (`backend/e2e/`) exercising real HTTP flows against the actually-running server across Phases 2/4/5/6/7/10 together, including a genuine create-schema-CRUD-drop cycle against all three real local databases and read-only checks against the real Portfolio remote connection. A real, pre-existing gap in Phase 8's policy layer was found and documented (not fixed) in the process — see `DECISIONS.md`. Once both suites passed, **Phase 3's `testRoutes.ts`/`public/test.html` (and their mounts in `index.ts`) were deleted for real** — the `pg`/`mysql2`/`better-sqlite3` drivers are now used solely by `sqlConsole/`/`dataManagement/`, not by any Phase 3 code, which no longer exists. **As of Phase 12a (2026-09-09):** the project's first real frontend code exists — `frontend/` (Vite + React + TypeScript), scaffolded fresh at the repo root, sibling to `backend/`. It renders only the global background matched to the design canvas prototype's actual content (`design/Main.dc.html`'s `.app` container, not `master-admin-panel.html`'s own editor-tool chrome): a flat `#1e1e1e` background, `#cccccc` text, the `"Segoe UI", system-ui, -apple-system, sans-serif` font stack, full viewport height. `App.tsx` renders a single empty `.app-shell` div styled by a plain `App.css` (Vite's template boilerplate — counter demo, logos — was stripped). No sidebar, tabs, panels, or other prototype UI chrome exists yet, per this phase's narrow scope; that starts with Phase 13. **As of Phase 12b (2026-09-09):** `frontend/src/LoginPage.tsx`/`LoginPage.css` — a standalone, fresh-designed static login page (no prior mockup existed), deliberately *not* imported by `App.tsx` (which stays exactly Phase 12a's background-only piece), kept separate per this phase's own scope. Reuses the prototype's existing `.modal`/`.input`/`.btn-primary` tokens (not invented ones) for the centered card, inputs, and submit button, on the same `#1e1e1e` app background. Client-side validation via a new `zod` dependency (`frontend/src/loginSchema.ts`) — username required, password requires 8+ characters plus uppercase/lowercase/digit/special-character — checked on submit with inline errors; still no `fetch`, session, or redirect of any kind. Hardened against browser autofill noise (`autoComplete`, password-manager ignore attributes, readonly-until-focus). See `DECISIONS.md` for the plan to reuse this schema server-side, plus add rate limiting, once Phase 24 wires this page to the real `/auth-api/login`. **As of Phase 13 (2026-09-09):** `frontend/src/AppShell.tsx`/`AppShell.css` — the root layout scaffold (the owner's requested "base.html"-equivalent) that every later static UI piece mounts into, read verbatim off the prototype's real markup/CSS. `App.tsx` now renders `<AppShell />` in place of the old bare background div; Phase 12a's background lives inside it as the base layer (`App.css` deleted, folded into `AppShell.css`). Structure: `.titlebar` (built for real — app icon/name, empty breadcrumb slot, static "Ctrl K" button) → `.main-row` with three empty-shell regions at the prototype's exact dimensions/colors (`.activitybar`, `.sidebar`, `.editor-col`) → `.statusbar` (also an empty shell) — see `DECISIONS.md` for why the titlebar was built now rather than deferred, and `PHASES.md` for which later phase fills each empty region. `LoginPage.tsx` and `main.tsx`'s pathname router are unaffected. **As of Phases 14–22 (2026-09-09–11):** every remaining static UI piece (favicon, activity bar, explorer sidebar, editor tabs, SQL Console panel, command palette, status bar, editor pane, split panes) was filled into `AppShell.tsx`/`AppShell.css`, matching the design canvas prototype exactly — see `PHASES.md`'s own per-phase entries for full detail on each; not re-derived here to avoid duplicating that record. **As of Phase 23 (2026-09-11):** the Data Management path (Phase 6/7) gained a real staging layer, and the Phase 22 split-pane UI became the first genuinely wired (non-static) piece of the frontend, ahead of Phase 24's general wiring pass. Backend: two new tables in `adminpanel_app` Postgres (`backend/src/db/schema.ts`) — `drafts` (one row per `(engine, collection, record_id)`, a full shadow copy of the record's would-be values as `draft_values JSONB`) and an append-only `deploy_log` (a lightweight, UI-less forward-compat hook for a future deploy-history feature). New `backend/src/dataManagement/staging.ts` (`saveDraft`/`getDraft`/`listDrafts`/`discardDraft`/`getDraftWithLiveDiff`/`deployDraft`) reuses Phase 6's `getTableSchema`/`validateValues`/`getRecord`/`updateRecord` directly — no new per-engine SQL exists anywhere in this module; `deployDraft` calls `updateRecord` verbatim for the actual live write. New `backend/src/dataManagement/stagingRoutes.ts`, mounted alongside `dataRoutes.ts` at `/data-api`: `POST/GET/DELETE /:engine/:collection/records/:id/draft` and `POST /:engine/:collection/records/:id/deploy` (gated 404 no-draft → 403 Phase 8 protected-table policy, reusing `isProtectedTable` verbatim → 409 missing `confirm:true`, mirroring the SQL Console's `gatedQuery` ordering — this is the one place the Data Management path now shares a safety primitive with the SQL Console, without folding the two paths together). A small `backend/src/dataManagement/routeHelpers.ts` was extracted from `dataRoutes.ts` so both routers share one `isValidEngine`/`assertKnownCollection`/`handleError`. Frontend: `AppShell.tsx`'s Compare tab is now real for exactly one hardcoded demo record (`postgres`/`posts` id `1`, a single `DEMO` constant) — real `fetch`-based load/save/deploy via local `useState`/`useEffect` (no state/data-fetching library yet, both still Phase 24/26's job), Production pane read-only/controlled, Staging pane genuinely editable, a new `.btn-deploy` alongside the existing (now-wired) `.btn-save`. A new one-off seed script, `backend/src/scripts/seedDemoPost.ts` (`npm run seed:demo-post`), creates a real `posts` table/row in the postgres target database matching this content that every prior static phase had only ever hardcoded in JSX. See `DECISIONS.md`'s "Phase 23 implementation" entry for the full reasoning behind each of these choices.

**Planned:** A browser-based web app (**superseding an earlier Electron desktop-app plan**, reversed 2026-09-08 — see `DECISIONS.md`): a React + TypeScript frontend (built via Vite), styled and structured after the VS Code interface, served by a Node.js backend server, gated behind a single-user login. The frontend talks to two distinct backends: (1) arbitrary remote sites over HTTPS via the Content Admin API protocol (client-side `fetch`, unchanged from the original plan), and (2) this panel's own backend server, which holds the native DB drivers and brokers the SQL console's direct database connections (replacing Electron's main-process/IPC arrangement). Deployment target: Render's free tier + an UptimeRobot keep-alive monitor, the same pattern as the Portfolio project, backed by a Neon Postgres database for the panel's own production data. No planned-architecture code has been written yet — but the full build order is locked: `PHASES.md`'s Phase 0–31 roadmap covers local database setup, the backend server and its login/SQL-console/data-management/Content-Admin-API/secrets pieces, an end-to-end backend test pass, every static UI piece matched to the design canvas prototype, wiring the UI to the backend, Monaco and Zustand build-outs, Image/Video field support, and finally production deployment plus live verification.

## Technology Stack

**Implemented:** `backend/` — Node.js (v24) + Express 4 + TypeScript, run via `tsx` in dev and compiled with `tsc` for production, ESM module format. DB access uses `pg`, `mysql2`, and `better-sqlite3` (the same drivers the planned architecture locks in below) — used by `sqlConsole/` and `dataManagement/` (Phase 3's own throwaway usage of these drivers was deleted in Phase 11, see below), plus `dotenv` for loading `.env.local`. **As of Phase 4:** `express-session` (session middleware) + `connect-pg-simple` (Postgres-backed session store) + `bcryptjs` (password hashing) added. **As of Phase 11:** `vitest` and `@playwright/test` added as devDependencies — see the Testing row below. **As of Phase 12a (2026-09-09):** `frontend/` — React 19 + TypeScript, scaffolded via Vite's `react-ts` template, plain CSS (no Tailwind or other CSS framework introduced yet — matches the prototype's own plain-`<style>` approach). **As of Phase 12b (2026-09-09):** `zod` added to `frontend/` for client-side form validation (see `DECISIONS.md` — intended to be reused server-side, plus rate limiting, when Phase 24 wires real login). Monaco and Zustand still not wired in.

**Planned** (see `DECISIONS.md` — Electron-specific rows below are superseded; carried-over and new rows reflect the 2026-09-08 browser-based pivot):

| Layer | Choice | Why |
|---|---|---|
| Frontend | React + TypeScript, built with Vite | Matches the component/state model already proven in the prototype; fast dev loop. Unchanged by the browser-based pivot. |
| Backend server | Node.js (specific framework — e.g. Express/Fastify — not yet chosen) | Needed so the browser can reach native DB drivers indirectly; replaces Electron's main process. See Open decisions in `DECISIONS.md`. |
| Code/SQL editing | Monaco (the actual VS Code editor component) | Real syntax highlighting for the SQL console and any raw JSON/code fields. Monaco is web-native, so this is unaffected by the pivot. |
| State management | Zustand | Lightweight global store for open tabs, active site, connections. Unchanged. |
| DB access (SQL console) | Node drivers per engine (`pg`, `mysql2`, `better-sqlite3`), now running in the backend server and exposed to the frontend via an authenticated HTTP/WebSocket API instead of Electron's `contextBridge`/IPC | Implements the "connect directly to the DB" decision (see `DECISIONS.md`), relocated from an Electron main process to a standalone backend server. |
| Content Admin API client | Plain `fetch` from the frontend | Outbound HTTPS only, to sites the user controls. Unchanged. |
| Auth | Single-user login — server-side session cookie (`express-session` + `connect-pg-simple`), `bcryptjs` password hashing, credentials in `adminpanel_app` Postgres (resolved [Phase 4], see `DECISIONS.md`) | The browser-based site is reachable by anyone with the URL, unlike a desktop app installed only on the owner's machine — see `DECISIONS.md`. |
| Secrets (API keys, DB credentials) | An encrypted `secrets` table in `adminpanel_app` Postgres, AES-256-GCM via `node:crypto` (resolved [Phase 10], see `DECISIONS.md`) | Replaces Electron's `safeStorage`; reuses the already-established `adminpanel_app` persistence pattern rather than new infrastructure, no new dependency needed. |
| Local/app state (layout, recent sites, open tabs) | Not yet decided — `electron-store` no longer applies (Electron-only) | Likely browser storage and/or server-persisted settings; not yet chosen. |
| Hosting / deployment | Render free tier + UptimeRobot | Owner's explicit choice, reusing the exact pattern the Portfolio project already runs on. Replaces `electron-builder`/desktop packaging entirely. |
| Testing | Vitest (unit/"component", co-located `*.test.ts`) + Playwright Test API-testing mode (`backend/e2e/`, no browser) — resolved [Phase 11], see `DECISIONS.md` | First testing infrastructure in the project; replaces every prior phase's ad-hoc `curl`/`psql` verification with a permanent, re-runnable suite. |

The Electron-vs-Tauri shell decision (and the Tauri rejection reasoning) is now moot given the browser-based pivot — see `DECISIONS.md` for the full history.

Real module structure now exists: `backend/src/db/pool.ts` (shared `pg.Pool` for `adminpanel_app`), `backend/src/db/schema.ts` (`ensureSchema()` — `users` and, as of Phase 10, `secrets`), `backend/src/auth/authRoutes.ts` (login/logout/session-check), `backend/src/scripts/seedOwner.ts` (one-off account-seeding CLI), `backend/src/scripts/migrateSecrets.ts` (Phase 10's one-off env-to-encrypted-store migration CLI), `backend/src/types/express-session.d.ts` (typed session data), `backend/src/secrets/` (`crypto.ts`, `store.ts` — Phase 10's encryption/storage API), and `backend/src/sqlConsole/` — `connections.ts` (per-engine connections to the Phase 1b target databases, built via an async `initConnections()` that reads from Phase 10's secrets store rather than `process.env`), `classify.ts` (write-statement/multiple-statement guards), `adapters.ts` (per-engine query execution and result normalization), `sqlConsoleRoutes.ts` (table-listing/query endpoints), and `backend/src/dataManagement/` — `introspection.ts` (schema/primary-key introspection per engine), `fieldTypes.ts` (native-type mapping + naming-convention special-type tagging), `validation.ts` (create/update value validation), `crud.ts` (list/get/create/update/delete by id), `upload.ts` (multer config + media path helpers), `dataRoutes.ts` (collections/schema/records/upload endpoints). Content Admin API logic still doesn't exist yet (Phase 7 onward). **As of Phase 11:** each module above with pure-function logic gained a co-located `*.test.ts` (Vitest), and a new `backend/e2e/` directory (`globalSetup.ts`, `fixtures.ts`, `helpers/api.ts`, plus five `*.spec.ts` files) holds the Playwright API-mode e2e suite. `backend/src/testRoutes.ts` and `backend/public/` no longer exist (Phase 3's throwaway diagnostic routes, retired). **As of Phase 12a (2026-09-09):** `frontend/` exists — a standard Vite `react-ts` scaffold (`index.html`, `src/main.tsx`, `src/App.tsx`, `src/App.css`, `src/index.css`), stripped of the template's demo content. `App.tsx` renders one empty `.app-shell` div. **As of Phase 12b (2026-09-09):** `frontend/src/LoginPage.tsx`/`LoginPage.css`/`loginSchema.ts` added — a standalone component, not imported by `App.tsx` or `main.tsx`. **As of Phase 13 (2026-09-09):** `frontend/src/AppShell.tsx`/`AppShell.css` added — the base layout scaffold; `App.tsx` now renders it instead of a bare div, and `App.css` no longer exists (its one rule moved into `AppShell.css`). `main.tsx`'s pathname router and `LoginPage.tsx` are unchanged. **As of Phases 14–22:** every remaining static UI piece was added into these same two files (no new component files were introduced — see `PHASES.md` for each phase's detail). **As of Phase 23 (2026-09-11):** `backend/src/dataManagement/staging.ts`, `stagingRoutes.ts`, and `routeHelpers.ts` added (backend); `backend/src/scripts/seedDemoPost.ts` added (one-off local seed); `AppShell.tsx`/`AppShell.css` and `vite.config.ts` (new dev-server proxy for `/data-api`) modified (frontend) — see the System Overview entry above for what each does. No other component files exist yet.

**Planned:** Not yet broken down into concrete modules/files — no code has been written against the now-locked Phase 0–31 roadmap yet (see `PHASES.md`). The product design (see `PROJECT.md`) implies at least: a frontend UI layer (activity bar / explorer / tabs / editor pane / command palette / status bar / SQL Console panel / split panes), a Content Admin API client module, a login/auth flow, a backend-server DB-connection module per supported engine, and a data-management/schema-driven CRUD engine — but no file/module layout has been decided. The roadmap's own ordering is a real architectural signal worth preserving here: backend pieces (server, login, SQL console, data management engine, Content Admin API, secrets) are built and end-to-end tested before any static UI, and every UI piece is built to match the design canvas prototype exactly *before* being wired to the backend — see `PHASES.md` for the full sequencing.

## Data Flow

**Implemented:** None — no real data flow exists; the prototype has no data fetching or persistence.

**Planned:** Two independent flows, per `PROJECT.md`'s Content Admin API protocol vs. SQL console distinction:
1. **Content Admin API path**: frontend → `fetch()` over HTTPS → a remote site's Content Admin API → schema + records returned → panel renders the appropriate editor for each field type (text, rich text, image, video, relation dropdown, date, boolean, array, etc.) based on the schema the API itself describes. Image and Video are real, first-class field types (backend support in Phase 6, dedicated frontend picker/upload/preview UI in Phase 27 — see `DECISIONS.md`), not just a narratively-mentioned "image picker." **Implemented as of [Phase 23] (2026-09-11):** a save through this path now stages a draft (`drafts` table in `adminpanel_app` Postgres — a full shadow copy of the record's would-be values, keyed by `(engine, collection, record_id)`) rather than writing the target database immediately — the Phase 22 split-pane UI is wired to compare the draft against the live row, and a separate, confirm-gated "deploy" action (`POST /data-api/:engine/:collection/records/:id/deploy`) applies it via the same `updateRecord` function ordinary CRUD saves already use. See `backend/src/dataManagement/staging.ts`/`stagingRoutes.ts` and `DECISIONS.md`'s "Phase 23 implementation" entry. Currently wired end-to-end in the frontend for one hardcoded demo record only — generalizing it to every record is [Phase 24]'s job.
2. **SQL console path**: frontend → authenticated HTTP/WebSocket request → this panel's own backend server → native DB driver (`pg`/`mysql2`/`better-sqlite3`) → direct connection to the target database, bypassing the Content Admin API and any schema validation it would otherwise enforce. Relocated from Electron's IPC/main-process arrangement to a standalone backend server as part of the 2026-09-08 browser-based pivot (see `DECISIONS.md`) — still a deliberate exception, acceptable specifically because this is a personal, single-operator tool. **Implemented as of [Phase 5]**: `POST /sql-console-api/:engine/query` and `GET /sql-console-api/:engine/tables`, across all three Phase 1b target engines, enforcing a read-only-by-default/`confirm:true`-for-writes posture (see `DECISIONS.md`). **Extended as of [Phase 7]**: `GET/POST /sql-console-api/sites/:siteId/{tables,query}` reaches a real, external site's own database (currently Portfolio's local dev Postgres) the same direct-driver way — not via a bridge through that site's own API server, since the site's own codebase was ruled off-limits (see `DECISIONS.md`). **As of [Phase 8]**: both query routes now enforce a protected-table-name write policy (`backend/src/sqlConsole/policy.ts`) ahead of the confirm gate — tables named like accounts/secrets storage can never be written to, confirmed or not. Not yet authenticated — no route currently requires a session; that's [Phase 24]'s job. The "authenticated HTTP/WebSocket" framing above describes the eventual planned state, not the current one.

A third flow now exists that didn't under the desktop-app plan: **login** — the browser client authenticates against the backend server (`POST /auth-api/login`) before reaching either flow above (see `DECISIONS.md`'s "Single-user login" and "Login mechanics" decisions). Implemented as of [Phase 4]: credentials checked against `adminpanel_app`'s `users` table (bcrypt), a session cookie issued and persisted server-side (`connect-pg-simple`). Nothing is gated by this yet — no other route currently requires a session; that wiring is [Phase 24]'s job once a real UI exists.

## State Management

**Implemented:** None.

**Planned:** Zustand for frontend global state — open tabs, active site/workspace, connection status. Per `PHASES.md`'s locked roadmap, Phase 24 wires the UI up with only minimal/ad-hoc state just to make it work, and Phase 26 replaces that with a real, fully-wired Zustand implementation — the same "minimal first, fully functional in a dedicated later phase" pattern used for Monaco (Phase 24 → 25). Persisted local app settings (layout, recent sites, open tabs) need a new mechanism now that `electron-store` no longer applies — not yet decided (browser storage vs. server-persisted, per Open decisions in `DECISIONS.md`). Secrets (API keys, DB credentials) get a real server-side storage mechanism in Phase 10 — not yet built, but no longer entirely undecided-in-direction — keeping the "two distinct secret categories" principle (API keys vs. DB credentials) regardless of mechanism.

## Routing

**Implemented:** No real router yet (still an open decision — see `DECISIONS.md`). **As of Phase 12b (2026-09-09):** `frontend/src/main.tsx` uses a minimal, dependency-free `window.location.pathname` check to pick which top-level component to render — `/login` → `LoginPage`, anything else → `App` — giving each static page its own real URL (`http://localhost:5173/`, `.../login`) instead of one page being viewable only by temporarily swapping and reverting what's mounted. Per the owner's direct standing instruction, every future static UI page (Phases 13–22) must get its own URL this same way, added alongside existing ones, never by removing an existing page's path.

**Planned:** A real router choice is still not made — likely still tab/panel-based navigation (VS Code-style, no URL-based routing) within the app shell once Phase 13+ exists, plus a real route/redirect for the login gate itself now that the app is browser-based. The `main.tsx` path-check above is an interim mechanism for keeping static pages independently viewable during Phases 12–22, not a substitute for that decision — if/when a real router is chosen, this pattern should migrate to real routes rather than being carried forward as-is.

## API Architecture

**Implemented:** None.

**Planned:** The **Content Admin API** — a protocol the panel speaks as an HTTP client, not a specific server this repository implements. Any backend can serve it by exposing: auth (get a session/token), list collections, get a collection's schema (field names, types, validation, relations), CRUD on records within a collection, media upload/listing, and search. The schema-driven nature of this API (the server describes its own schema rather than the panel hardcoding it per site) is the core architectural decision this whole project is built around (see `DECISIONS.md`).

**As of [Phase 9] (2026-09-09):** a formal spec document exists — `Project Docs/CONTENT-ADMIN-API-SPEC.md` — but it documents a narrower reality than the paragraph above describes. It specifies the real request/response contract of `/data-api/*` and `/auth-api/*` as actually implemented: AdminPanel's own backend, directly introspecting its own locally-reachable [Phase 1b] databases, with its own single-operator login — not a protocol any remote site's backend has implemented or that this panel calls as an HTTP client. Search and media listing (both named above) were never built. See `DECISIONS.md`'s "Phase 9 spec documents AdminPanel's actual internal data-api contract, not a remote-site-implemented protocol" entry for the full reasoning. The API's tech stack is a per-site decision, out of scope for this repository — this remains true of the still-unbuilt, genuinely remote-implementer version of the contract. **As of [Phase 23] (2026-09-11):** the spec's §4.2 documents `/data-api`'s new staging/draft/deploy sub-resource (see above) — still entirely internal to AdminPanel's own database, same scope caveat as the rest of the document.

Two tiers of API implementer are anticipated: (1) sites the owner builds, implementing the contract natively — the primary v1 target; (2) third-party platforms (WordPress, Shopify, etc.), which would need a per-platform adapter translating their native API into the Content Admin API contract — not required for v1.

## Data / Persistence

**Implemented:** None.

**Planned:** The panel does not own a *content* database — it either (a) reads/writes remote sites' content through their own Content Admin API implementations, or (b) connects directly to a target database via native drivers for the SQL console. It does need some persistence of its own that didn't exist under the desktop-app plan: at minimum, the single login account's credentials, plus wherever per-site DB credentials/API keys end up being stored server-side. **Implemented as of Phase 4:** the login account's credentials (`users` table) and session data (`session` table, via `connect-pg-simple`) are both persisted in `adminpanel_app`, the local Postgres database provisioned in Phase 1a — the first real use of that database. **Implemented as of Phase 10:** a `secrets` table in the same `adminpanel_app` database holds per-site DB credentials (and, going forward, Content Admin API keys) encrypted at rest — see the Technology Stack table above and `DECISIONS.md`. **Implemented as of Phase 23:** two more tables in the same `adminpanel_app` database — `drafts` (one row per `(engine, collection, record_id)`, a full shadow copy of a record's pending edit as `draft_values JSONB`) and an append-only `deploy_log` (`deployed_values JSONB` per past deploy) — neither holds *content* the panel owns long-term; `drafts` rows are deleted once deployed, and `deploy_log` has no read endpoint/UI yet (a deliberate, cheap forward-compat hook, not a real history feature — see `DECISIONS.md`). Per `PHASES.md`'s locked roadmap, one piece remains: the panel's own *production* database — a Neon Postgres instance, same pattern as the Portfolio project — is set up in Phase 29, since Render's free tier (the Phase 30 deployment target) has no persistent disk.
